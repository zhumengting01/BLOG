## 一、项目是什么

AI Weekly 是一个已投入生产环境运行的全自动化 AI 行业周刊生成与发布系统。

它从 11 个中英文权威 RSS 源采集信息，通过 LLM 自动完成分类、摘要和点评，生成结构清晰的周刊内容，并由静态站点面向真实读者提供服务。整个过程无需人工干预，系统已进入每周一自动发布新刊期的稳定运行周期。

## 二、为什么做这件事

AI 领域信息爆炸但极度分散，每周产生数百条动态，真正重要的内容被淹没。纯人工编辑成本高，简单聚合又缺乏结构化。

**目标**：构建一条从信息采集到内容交付的生产级自动化管线，用 LLM 替代人工编辑的判断力，以最小时间成本提供最高信息密度的中文周刊。

**我的角色**：项目设计者与全栈开发者，独立完成从开发到上线的完整闭环——架构设计、内容管线开发、前端站点构建与上线、生产环境部署与自动化运维。

## 三、技术架构

**核心设计原则**：内容生产与前端呈现完全解耦，通过文件系统作为唯一接口，使两部分可独立演进。

| 层级 | 技术方案 | 关键设计 |
| ---- | ---- | ---- |
| **采集层** | Python + feedparser | 11个RSS源，兼容RSS 2.0/Atom，独立超时与异常隔离 |
| **整理层** | MiMo API（Anthropic协议） | 精细Prompt控制5个板块分类、摘要、点评，强制来源多样化 |
| **生成层** | Python + Markdown | LLM输出转frontmatter Markdown，自动推断期号，支持预览模式 |
| **站点层** | Astro + Tailwind | SSG静态页面，零JS默认输出，构建时生成搜索索引，View Transitions + 暗色模式 |

**数据流**：RSS采集 → JSON → LLM整理 → Markdown落盘 → Astro构建 → 静态页面部署。

## 四、Prompt 工程详解

整理层的 Prompt 设计是整个系统的核心。以下展开关键设计策略。

### 4.1 五个板块的分类控制

在 System Prompt 中为每个板块明确定义边界、范围和示例：

| 板块 | 覆盖范围 |
| ---- | ---- |
| 学术前沿 | 学术论文发布、研究机构成果、基础科学突破 |
| 产业动态 | 大型科技公司产品发布、战略合作、重大业务调整 |
| 开源生态 | 开源项目更新、社区动态、工具库发布 |
| 创业融资 | AI 初创公司融资消息、新公司成立、并购事件 |
| 政策监管 | 各国 AI 政策法规、行业标准制定、监管动态 |

**分类规则**：

* 每条新闻只能归入一个板块
* 难以判断时归入最相关的板块
* 同一事件只在一个板块中出现一次

### 4.2 摘要生成的质量控制

通过 Prompt 约束摘要的长度、风格和信息密度：

* **长度**：50-80 字中文
* **风格**：客观中立，避免主观评价
* **内容**：必须包含核心信息（谁、做了什么、为什么重要）
* **禁止项**：不重复来源名称（已单独记录），不使用"据悉""据报道"等套话

**摘要结构要求**：主体 → 动作 → 创新点 → 影响。

### 4.3 一周观察的结构化输出

一周观察需要从多条新闻中提炼洞察：

* **长度**：200-300 字中文
* **结构**：分 2-3 个要点，每点一句话概括
* **内容方向**：本周最值得关注的趋势、多条新闻之间的关联分析、对未来发展的简要展望
* **风格**：专业、有洞察力，避免泛泛而谈

### 4.4 来源多样化约束

这是 Prompt 设计中最重要的环节，目标是**避免模型偏袒头部公司**。

在输入数据中为每个条目标识来源，并在 Prompt 中加入强制约束：

* 每个板块至少包含 2 个不同来源的内容
* 单一来源在整份周刊中的占比不得超过 30%
* 优先选择中小公司、开源项目、学术机构的内容，避免被头部公司主导
* 如果某一来源内容过多，筛选最有价值的，其余舍弃

### 4.5 输出格式约束

强制要求 LLM 返回结构化 JSON：

```json
{
  "sections": [
    {
      "name": "板块名称",
      "items": [
        {
          "title": "新闻标题",
          "source": "来源名称",
          "summary": "50-80字摘要",
          "link": "原文链接"
        }
      ]
    }
  ],
  "weekly_observation": "本周观察"
}
```

### 4.6 多层容错解析链

LLM 输出的 JSON 格式不稳定，可能带 markdown 标记、尾随逗号、非法转义字符等。设计了以下解析链：

> LLM原始输出 → 清除markdown标记 → 正则提取JSON → 修复尾随逗号 → 空骨架兜底

配合**指数退避重试**（失败后 2s/4s/8s 重试），确保 API 异常不导致流程崩溃。

**小结**：Prompt 设计的核心策略可以归纳为以下五个维度：

| 设计维度 | 核心策略 |
| ---- | ---- |
| 分类精准性 | 明确定义板块边界 + 分类规则 |
| 摘要质量 | 长度约束 + 结构要求 + 风格规范 |
| 一周观察 | 结构化输出 + 关联性分析 |
| 来源多样性 | 占比限制 + 强制校验 |
| 格式稳定性 | 多层容错解析链 + 指数退避重试 |

## 五、关键挑战与解决方案

### 挑战一：LLM 输出不可控

LLM 返回的 JSON 格式不稳定，可能带有 markdown 标记、尾随逗号、非法转义字符等。

**解决方案**：多层容错解析链 + 指数退避重试。

**可迁移经验**：Prompt 里写清楚要求只是第一步，代码层面必须设计清洗、修复和降级链路。永远不要信任 LLM 的输出格式。

### 挑战二：RSS 源格式异构

11 个源同时包含 RSS 2.0 和 Atom 格式，日期、描述、链接等字段位置不一致。

**解决方案**：字段 fallback 查找策略 + 每个源独立异常隔离。

**可迁移经验**：集成外部数据源时，不要假设数据结构一致，也不要把所有源放在同一个异常处理块里。

### 挑战三：生产环境可靠性

系统需要在无人值守的情况下每周稳定触发并执行。

**解决方案**：调度层（允许电池运行、错过补执行、失败重试）+ 代码层（指数退避重试、降级、全链路日志追踪）双重保障。

**可迁移经验**：调度层保证"触发"，代码层保证"执行容错"，两者互补才能做到真正的无人值守。

## 七、可迁移的经验

### 1. 解耦比优化更重要

内容生产和前端呈现通过文件系统解耦后，两边可以独立迭代。更换 LLM 模型不影响站点代码，更换前端框架不影响内容管线。

### 2. 构建时计算优于运行时计算

搜索索引在构建时生成，页面在构建时渲染。首屏零 JS 开销，无第三方依赖。适用于任何内容型站点。

### 3. 为不确定性设计

LLM 输出不稳定、外部源格式不统一、定时任务可能失效。设计降级路径，让系统在部分失败时仍能产出结果。

### 4. 容错的价值大于准确

一个返回空骨架但能继续运行的系统，比一个因解析失败而崩溃的系统有价值得多。生产环境的第一要务是"活着"，其次才是"完美"。

## 八、后续方向

模块化架构支持轻松扩展：更换 LLM 模型、添加新 RSS 源、切换前端框架。未来可引入人工反馈微调机制，进一步提升摘要精准度。
